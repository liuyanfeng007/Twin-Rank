# Twin-Rank 设计说明

本文解释系统**为什么这样设计**。使用方法见 [USAGE.md](USAGE.md)。

## 1. 总览

```
离线                                                              在线
─────────────────────────────────────────────                     ──────────────────────────────
原始数据                                                           用户请求(user_id[, history])
  │ 清洗、5-core、leave-last-out                                          │
  ▼                                                                       ▼
特征(编码器·物品特征·序列样本)                                     用户塔 → 用户向量（只算一次）
  │                                                                       │
  ▼                                                                       ▼
双塔训练 ──► 物品塔 ──► 全量物品向量 ──► Faiss 索引 ─────────────► 多路召回：双塔(~90) + 热门(~10)
  │                                                                       │ 候选 + 召回分
  ▼                                                                       ▼
验证集用户的候选 ──► 精排样本 ──► 精排训练 ─────────────────────► 精排特征 → 精排打分
  │                                                                       │
  ▼                                                                       ▼
测试集端到端评估 ──► 证据文件 ──► 注册(门禁) ──► champion ─────► MMR 重排 + 业务规则 → Top-K
```

## 2. 数据流与产物

| 阶段 | 输入 | 产物（默认在 `data/` 下） |
|---|---|---|
| 预处理 | 评论 + 商品元数据 | `processed/interactions.parquet`（含 split 列）、`items_meta.parquet` |
| 特征 | processed | `features/{train,val,test}.npz`、`item_features.npy`、`user_encoder.json`、`item_encoder.json`、`vocab.json`；`processed/interactions_encoded.parquet` |
| 双塔 | features | `artifacts/two_tower.pt`、`item_embeddings.npy` |
| 索引 | 物品向量 | `artifacts/items.faiss` |
| 精排 | 召回候选 | `artifacts/lightgbm_ranker.txt` 或 `deep_ranker_<类型>.pt`、`ranker_metrics_<类型>.json`（证据） |
| 注册 | 以上全部 | MLflow 注册表中的一个 pyfunc 模型版本 |

## 3. 关键设计决策

| 决策 | 原因 | 代价 / 注意 |
|---|---|---|
| **按时间 leave-last-out 切分**（每用户最后一次 = 测试，倒数第二 = 验证） | 训练只看到过去，避免未来信息泄露，模拟"预测下一个行为" | 用户之间的时间不对齐；测试集是"每用户一条"，指标波动大，需要足够的测试用户 |
| **编码器只用训练集拟合**，热度只用训练集统计 | 防止验证/测试信息泄露 | 验证/测试里没见过的商品被丢弃，**冷启动商品不在离线评估范围内** |
| **双塔 + batch 内负采样 + logQ 修正 + 假负例屏蔽** | 内部负样本免费且高效；热门商品更容易被当负样本采到，logQ 抵消这种偏置；同 batch 重复商品不是真负例 | batch 越大负样本越多但越吃内存；负样本是"随机的"，没有曝光意义上的难负例 |
| **物品塔离线建索引，线上只算用户塔** | 两塔独立才能提前算好所有物品向量；线上延迟只由一次用户塔 + 一次检索决定 | 用户和物品的交互只在最后一步内积，表达力弱于精排 |
| **多路召回 + 统一重算召回分** | 热门路补充覆盖率与冷启动；所有候选都用"用户向量·商品向量"打分，精排特征 `recall_score` 对两路一致 | 热门路候选的召回分通常偏低，精排需要自己学会处理 |
| **Faiss 不支持逐用户排除，多取再过滤** | 已看商品不能再推荐 | 历史越长，多取越多；商品很多时用 HNSW |
| **精排样本来自验证集用户**，只保留候选里含目标的用户 | 双塔没在这些目标上训练过，候选分布接近线上；没有正样本的分组对排序学习没有信号，还会虚高 LightGBM 的 NDCG | 实际参与训练的用户通常只有 `max_train_users` 的 20% 左右（取决于候选命中率）；样本少时深度模型易过拟合 |
| **精排统一接口 `Ranker`** | 四种模型共用训练流水线、评估、服务、注册；换模型只改一行配置，对比公平 | 深度模型用逐点 BCE，LightGBM 可用 LambdaRank，损失不同是已知的不对称 |
| **离线造样本与在线打分共用同一份特征代码** | 避免 training-serving skew | 特征改动必须兼顾两端；`build_ranking_features` 是唯一出口 |
| **MMR + 品牌上限 + 黑名单 + 置顶** | 相关性之外的多样性和运营诉求 | 用相关性换多样性，离线 Recall 会略降（尤其 @50） |
| **整套系统打包为一个模型版本** | 索引必须与用户塔同一次训练、精排必须与召回候选配套；v3 就是配套的 v3 | 版本体积较大（含物品向量、索引、历史快照） |
| **质量门禁 + 证据文件 + 文件指纹** | "最新 ≠ 最好"；指标必须对应被注册的那份文件 | 比较用同一批测试用户，反复挑选会略微高估；口径不同时只能人工判断 |
| **macOS 默认单线程、GPU 兼容检测** | 多份 libomp 会卡死；新版 PyTorch 不再支持老架构 GPU | 单线程较慢；回退 CPU 时训练变慢 |

## 4. 模块职责

* `pipelines/` 只做串联，业务逻辑都在对应子包里，便于单测与复用。
* `components.py` 装配召回/重排所需的全部组件，**离线训练精排与在线服务共用**。
* `serving/recommender.py`（`RecommendService`）是唯一的推荐主流程：API、注册模型（pyfunc）、命令行预测最终都调用它。
* `registry/` 不依赖训练代码：打包的只是文件和配置，加载时重建 `RecommendService`。

## 5. 评估口径

* 召回：Recall@K / NDCG@K，在全量商品上暴力检索，排除已交互商品。
* 端到端（`train_ranker`）：同一批测试用户上对比 **仅召回 / 召回+精排 / 召回+精排+重排**，并给出 `candidate_hit_rate`（候选里是否含目标，即精排上限）。
* 晋升比较的前提是评估口径一致（数据集、测试用户数、K 值、随机种子），否则不比较。

## 6. 已知局限

* **只有隐式正反馈**：没有曝光日志，"负样本"是候选里没被选中的商品，会把"未曝光"误当"不喜欢"。
* **用户塔较简单**：用户 ID + 历史商品平均池化；历史商品只用 ID，不含类目品牌；没有用户画像；不区分行为先后。
* **召回是瓶颈**：`candidate_hit_rate` 决定精排上限，精排只能在候选里排序。
* **没有新商品冷启动**：商品 ID 编码器只认训练集里出现过的商品。
* **历史存储在进程内**：服务重启后点击反馈会丢失；多实例之间不共享。生产环境应换成 Redis / 特征平台。
* **离线指标 ≠ 线上效果**：最终需要 A/B 测试验证。
* **深度精排在小样本上不一定优于 LightGBM**，是否值得切换请用 `make compare-rankers` 在自己的数据上验证。
